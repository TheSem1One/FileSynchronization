# FolderSync --- архітектура та план розробки

## 1. Мета завдання

Розробити консольну програму на C#, яка періодично синхронізує дві папки
в одному напрямку:

**Source → Replica**

Після успішної синхронізації вміст Replica має відповідати вмісту
Source:

-   усі файли з Source існують у Replica;
-   нові та змінені файли скопійовані;
-   зайві файли та папки в Replica видалені;
-   структура вкладених папок збережена.

Replica не повинна змінювати Source. Зміни, які користувач зробив
безпосередньо в Replica, під час наступної синхронізації будуть
виправлені відповідно до Source.

## 2. Принципи розробки

Для цього завдання достатньо невеликої багатопроєктної архітектури. Не
потрібно використовувати Clean Architecture з великою кількістю шарів,
CQRS, MediatR або складний Dependency Injection.

Основні принципи:

1.  **Single Responsibility Principle** --- кожен клас має одну
    зрозумілу відповідальність.
2.  **Dependency Inversion** --- основна логіка залежить від інтерфейсу
    логера, а не від конкретної реалізації.
3.  **Separation of Concerns** --- аргументи, налаштування,
    синхронізація та логування не змішуються в одному класі.
4.  **Fail safely** --- помилка з одним файлом не повинна без потреби
    зупиняти всю програму або призводити до втрати даних.
5.  **Testability** --- алгоритм має бути зручним для перевірки
    автоматичними тестами.
6.  **YAGNI** --- не додавати абстракції та функціональність, яких не
    вимагає завдання.

Рекомендована структура:

``` text
FolderSync/
│
├── src/
│   ├── FolderSync.Console/
│   │   ├── Program.cs
│   │   ├── ArgumentParser.cs
│   │   └── Services/
│   │       └── FileLogger.cs
│   │
│   └── FolderSync.Core/
│       ├── Models/
│       │   └── SyncOptions.cs
│       ├── Interfaces/
│       │   └── IFileLogger.cs
│       └── Services/
│           └── FolderSynchronizer.cs
│
├── tests/
│   └── FolderSync.Tests/
│       ├── FolderSynchronizerTests.cs
│       └── ...
│
├── FolderSync.sln
└── README.md
```

### Залежності між проєктами

``` text
FolderSync.Console ──────> FolderSync.Core
FolderSync.Tests   ──────> FolderSync.Core
```

-   **FolderSync.Console** --- точка входу, розбір аргументів, створення
    об'єктів та керування життєвим циклом програми.
-   **FolderSync.Core** --- налаштування, контракти та основний алгоритм
    синхронізації.
-   **FolderSync.Tests** --- автоматичні тести основної логіки.

`Core` не повинен залежати від `Console`. Він може використовувати
стандартні API .NET, наприклад `System.IO` та
`System.Security.Cryptography`.

Реалізацію `FileLogger` можна розмістити в Console-проєкті, оскільки
саме консольний застосунок відповідає за конкретні способи виведення
повідомлень. Інтерфейс `IFileLogger` розміщується в Core.

## 4. Відповідальність класів

### 4.1. Program.cs

Відповідає за запуск програми та з'єднання компонентів.

Його обов'язки:

-   отримати аргументи командного рядка;
-   передати їх парсеру;
-   перевірити та отримати налаштування;
-   створити логер і синхронізатор;
-   запустити першу синхронізацію;
-   запускати наступні синхронізації з заданим інтервалом;
-   коректно обробити Ctrl+C та завершити програму.

`Program.cs` не повинен містити алгоритм копіювання, порівняння або
видалення файлів.

### 4.2. ArgumentParser

Відповідає за перетворення аргументів командного рядка на об'єкт
`SyncOptions`.

Очікуваний формат запуску:

``` bash
FolderSync <source> <replica> <interval-seconds> <log-file>
```

Приклад:

``` bash
dotnet run -- ./source ./replica 10 ./logs/sync.log
```

Парсер має перевірити:

-   що передано рівно чотири аргументи;
-   що інтервал є коректним додатним числом;
-   що шляхи не порожні;
-   що шляхи можна перетворити на абсолютні.

Розбір аргументів і перевірку файлової системи бажано не змішувати.
Парсер може перевірити формат і значення, а окремий етап валідації ---
існування Source, допустимість Replica та конфлікти шляхів.

Для невеликого тестового завдання достатньо власного парсера без
сторонньої бібліотеки.

### 4.3. SyncOptions

Модель конфігурації програми:

``` csharp
public class SyncOptions
{
    public string SourcePath { get; init; } = string.Empty;
    public string ReplicaPath { get; init; } = string.Empty;
    public TimeSpan Interval { get; init; }
    public string LogFilePath { get; init; } = string.Empty;
}
```

Після валідації ці значення не повинні довільно змінюватися під час
роботи програми.

### 4.4. IFileLogger та FileLogger

Інтерфейс визначає контракт логування:

``` csharp
public interface IFileLogger
{
    void Log(string message);
}
```

`FileLogger` реалізує цей контракт і записує повідомлення:

-   у консоль;
-   у файл, шлях до якого переданий через аргументи.

Логувати потрібно фактичні операції: створення папок, копіювання файлів,
видалення файлів та папок. Корисно також записувати початок, завершення
та помилки синхронізації.

Рекомендований формат:

``` text
[2026-11-09 10:30:00] Synchronization started.
[2026-11-09 10:30:00] Created directory: Documents
[2026-11-09 10:30:01] Copied file: Documents/report.txt
[2026-11-09 10:30:02] Deleted file: old.txt
[2026-11-09 10:30:02] Synchronization completed.
```

Логер не повинен самостійно вирішувати, які файли копіювати або
видаляти. Це відповідальність синхронізатора.

### 4.5. FolderSynchronizer

Це основний компонент програми. Він отримує Source, Replica та логер і
виконує одну повну синхронізацію.

Публічний метод може мати такий вигляд:

``` csharp
public void Synchronize(
    string sourcePath,
    string replicaPath)
{
    // One synchronization pass.
}
```

Або синхронізатор може отримувати `SyncOptions` через конструктор.
Головне --- щоб одна операція `Synchronize` виконувала один повний
прохід, а періодичність залишалася відповідальністю Console-проєкту.

Внутрішню логіку варто розділити на невеликі методи:

-   `CreateMissingDirectories`
-   `CopyNewAndUpdatedFiles`
-   `DeleteExtraFiles`
-   `DeleteExtraDirectories`

Назви можуть бути іншими, але кожен метод повинен виконувати одну
зрозумілу операцію.

## 5. Алгоритм синхронізації

Один прохід синхронізації виконується в такому порядку.

### Крок 1. Перевірка шляхів

До початку роботи необхідно:

-   переконатися, що Source існує та є папкою;
-   перетворити шляхи на абсолютні;
-   переконатися, що Source і Replica не однакові;
-   заборонити ситуацію, коли одна папка розташована всередині іншої;
-   створити Replica, якщо її ще немає.

Останні дві перевірки критично важливі. Якщо Replica вкладена в Source,
синхронізатор може почати копіювати власні результати. Якщо Source
вкладена в Replica, видалення зайвого в Replica може зачепити Source.

Для порівняння шляхів потрібно враховувати файлову систему операційної
системи: на Windows зазвичай використовується порівняння без урахування
регістру, на Linux --- з урахуванням.

### Крок 2. Створення папок

Знайти всі папки в Source, включно з вкладеними, і створити відповідні
папки в Replica.

Важливо зберігати відносну структуру.

Наприклад:

``` text
Source/
└── Documents/
    └── Reports/
```

має створити:

``` text
Replica/
└── Documents/
    └── Reports/
```

Для побудови шляху в Replica використовувати відносний шлях від Source:

``` csharp
var relativePath = Path.GetRelativePath(sourcePath, sourceDirectory);
var replicaDirectory = Path.Combine(replicaPath, relativePath);
```

Для кореневої папки відносний шлях дорівнює `.`; її не потрібно
створювати повторно як вкладену папку.

### Крок 3. Копіювання нових та змінених файлів

Для кожного файлу Source:

1.  Отримати його відносний шлях.
2.  Побудувати відповідний шлях у Replica.
3.  Якщо файлу в Replica немає --- скопіювати.
4.  Якщо файл існує --- порівняти вміст.
5.  Якщо вміст відрізняється --- оновити копію.

Для порівняння вмісту можна використовувати SHA-256 зі стандартного API
.NET (`System.Security.Cryptography`).

Це надійніше, ніж порівнювати лише дату зміни або розмір: два різні
файли можуть мати однаковий розмір, а часові мітки можуть бути
неточними.

Не потрібно писати власну реалізацію SHA-256.

Для копіювання можна використовувати `File.Copy`. Якщо важливо зменшити
ризик залишити частково записаний файл після помилки, копіювати спочатку
в тимчасовий файл у Replica, а після успішного завершення замінювати
цільовий файл.

Після успішної операції записати її в лог.

### Крок 4. Видалення зайвих файлів

Потрібно знайти файли в Replica, для яких більше немає відповідного
відносного шляху в Source.

Такі файли потрібно видалити.

Приклад:

``` text
Source/
└── current.txt

Replica/
├── current.txt
└── old.txt
```

Після синхронізації `old.txt` має бути видалений.

Не варто порівнювати лише назви файлів: `A/report.txt` і `B/report.txt`
--- різні шляхи.

### Крок 5. Видалення зайвих папок

Після видалення зайвих файлів знайти папки Replica, яких більше немає в
Source.

Видаляти їх потрібно в порядку від найглибших до кореневих, щоб спочатку
видалити вкладені папки.

Не можна видаляти кореневу папку Replica --- вона повинна залишатися на
місці.

### Крок 6. Завершення

Записати повідомлення про завершення синхронізації. Якщо окремі операції
не вдалися, зафіксувати помилки й не повідомляти, що синхронізація
повністю успішна.

## 6. Порівняння файлів

Рекомендований підхід --- SHA-256.

Переваги:

-   перевіряється саме вміст файлу;
-   не залежить від точності часу модифікації;
-   доступний у стандартній бібліотеці .NET;
-   не потребує сторонньої бібліотеки.

Недолік --- для порівняння доведеться прочитати вміст файлів. Для
тестового завдання це прийнятний компроміс.

Для великих файлів краще використовувати потокове обчислення хешу, а не
завантажувати весь файл у пам'ять.

## 7. Періодичне виконання

Періодичність не повинна бути частиною `FolderSynchronizer`.
Синхронізатор виконує один прохід, а `Program.cs` відповідає за
повторення.

Для цього підходить `PeriodicTimer`:

``` csharp
using var timer = new PeriodicTimer(options.Interval);

await synchronizer.SynchronizeAsync(cancellationToken);

while (await timer.WaitForNextTickAsync(cancellationToken))
{
    await synchronizer.SynchronizeAsync(cancellationToken);
}
```

Це концептуальний приклад: сигнатуру `SynchronizeAsync` потрібно
узгодити з фактичною реалізацією.

Першу синхронізацію доцільно виконати відразу після запуску, а не чекати
перший інтервал.

Для завершення програми потрібно обробити Ctrl+C через
`CancellationTokenSource` та передати токен у періодичний цикл.

Не слід запускати нову синхронізацію, поки попередня ще працює.
Послідовний цикл з `await` забезпечує таку поведінку.

## 8. Обробка помилок і безпека

Робота з файловою системою може завершитися помилкою навіть після
успішної перевірки шляхів.

Передбачити обробку таких ситуацій:

-   файл зайнятий іншою програмою;
-   немає прав доступу;
-   файл видалили або змінили під час синхронізації;
-   недостатньо місця на диску;
-   Source став недоступним;
-   помилка читання, копіювання або видалення.

Рекомендації:

1.  Обробляти помилки на рівні конкретної файлової операції, де це
    можливо.
2.  Записувати в лог шлях і причину помилки.
3.  Не приховувати помилки порожнім `catch`.
4.  Не видаляти зайві файли, якщо не вдалося коректно отримати список
    Source.
5.  Не продовжувати небезпечне видалення, якщо структура Source
    прочитана не повністю.
6.  Не слідувати символічним посиланням або іншим reparse points без
    чітко визначеної політики. Для першої версії безпечніше їх відхиляти
    або пропускати з попередженням.
7.  Не допускати, щоб шлях призначення виходив за межі Replica.

Особливо важливо: якщо Source недоступний або його сканування
завершилося помилкою, не можна сприймати порожній список файлів як доказ
того, що всі файли Replica потрібно видалити.

## 9. Тестування

Тести мають перевіряти не тільки успішне копіювання, а й те, що Replica
точно відповідає Source.

Для тестів використовувати тимчасові директорії, створені в тестовому
середовищі. Після тесту їх потрібно очищати.

Рекомендований набір сценаріїв:

  -----------------------------------------------------------------------
  №                       Сценарій                Очікуваний результат
  ----------------------- ----------------------- -----------------------
  1                       Replica не існує        Replica створена

  2                       Source порожня          Replica порожня

  3                       У Source є новий файл   Файл скопійований

  4                       У Source є вкладені     Структура відтворена
                          папки                   

  5                       Вміст файлу змінився    Replica оновлена

  6                       Файл видалений із       Файл видалений із
                          Source                  Replica

  7                       Папка видалена із       Зайва папка видалена
                          Source                  

  8                       Файл існує тільки в     Файл видалений
                          Replica                 

  9                       Source і Replica        Немає зайвих змін
                          однакові                

  10                      Source та Replica       Валідація відхиляє
                          конфліктують за шляхом  конфігурацію

  11                      Немає доступу до файлу  Помилка залогована,
                                                  програма не приховує її

  12                      Файли з однаковим       Вміст Replica
                          розміром, але різним    виправлений
                          вмістом                 
  -----------------------------------------------------------------------

Додатково варто перевірити, що файли з однаковими назвами у різних
вкладених папках не плутаються.

## 10. Послідовність реалізації

Розробляти програму краще невеликими завершеними етапами.

### Етап 1. Створення Solution

-   Створити Console, Core та Tests.
-   Налаштувати посилання між проєктами.
-   Переконатися, що `dotnet build` працює.

**Результат:** порожній, але правильно структурований Solution.

### Етап 2. Налаштування та аргументи

-   Створити `SyncOptions`.
-   Реалізувати `ArgumentParser`.
-   Перевірити кількість та формат аргументів.
-   Реалізувати валідацію шляхів та інтервалу.

**Результат:** програма отримує коректну конфігурацію з командного
рядка.

### Етап 3. Логування

-   Створити `IFileLogger`.
-   Реалізувати `FileLogger`.
-   Додати виведення в консоль і файл.

**Результат:** програма може записувати події та помилки.

### Етап 4. Базова синхронізація

-   Створити Replica.
-   Реалізувати копіювання структури папок.
-   Реалізувати копіювання файлів.

**Результат:** Replica отримує початкову копію Source.

### Етап 5. Повна синхронізація

-   Реалізувати визначення змінених файлів.
-   Реалізувати видалення зайвих файлів.
-   Реалізувати видалення зайвих папок.
-   Додати безпечну обробку помилок.

**Результат:** після успішного проходу Replica відповідає Source.

### Етап 6. Періодичний запуск

-   Додати `PeriodicTimer`.
-   Виконувати першу синхронізацію одразу.
-   Додати коректне завершення через Ctrl+C.

**Результат:** програма працює безперервно та синхронізує папки з
заданим інтервалом.

### Етап 7. Тести

-   Покрити основні сценарії.
-   Перевірити граничні випадки.
-   Переконатися, що Source не змінюється.

**Результат:** є автоматична перевірка коректності.

## 11. Критерії готовності

Перед відправленням тестового завдання перевірити:

-   [ ] Синхронізація працює тільки в напрямку Source → Replica.
-   [ ] Нові файли копіюються.
-   [ ] Змінені файли оновлюються.
-   [ ] Видалені у Source файли видаляються з Replica.
-   [ ] Структура вкладених папок зберігається.
-   [ ] Зайві папки Replica видаляються.
-   [ ] Синхронізація виконується періодично.
-   [ ] Інтервал і шляхи передаються через CLI.
-   [ ] Операції створення, копіювання та видалення логуються в консоль
    і файл.
-   [ ] Помилки файлової системи обробляються.
-   [ ] Source не пошкоджується і не змінюється.
-   [ ] Є автоматичні тести.
-   [ ] README пояснює запуск програми.
